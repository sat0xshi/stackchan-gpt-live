# Stack-chan GPT Live / Terra 実機検証記録（2026-09-13）

## 目的と現在の状態

CoreS3版Stack-chanの顔・動作・UIを活かし、ファームの変更を抑えてGPT Liveで連続会話する。
USB接続した実機で、ユーザーが返事を聞けることと連続会話を確認した。
さらに、クラウドのTerraへの委任とWeb検索が実際に完了したことをログで確認した。
長時間動作には受信イベント取りこぼしが残る。安定版リリース完了という扱いではない。

## 実装と切り分け

1. 初期状態では顔は表示されるが、起動音も返事も聞こえないと報告された。
   認証とセッション開始は成功していた。音声レベル、I2S書き込み、アンプ状態を計測した。
2. 非同期のspeaking状態遷移によって受信済みの再生待ち音声を消さないよう修正した。
   CoreS3出力をステレオの左右スロットに同じPCMを送る方式へ変更した。
   これだけで無音の原因を確定したわけではない。
3. 会話用AFEを既存のNoAudioProcessorに置き換えて入力経路を切り分けた。
   バッファはStopとの競合を保護し、出力コールバック中はロックを解放する。
   現在はこの診断用の迂回を保持しており、AFEの不具合を確定したとは扱わない。
4. マイク、変換、圧縮、アプリ送信、プロトコル、ワーカー、受信、スピーカーを計測。
   返事が実際に聞こえるようになったが、途中停止が報告された。
5. 従来のAutoStopはspeaking時に入力を止め、listeningに戻る際に再生をリセットする。
   デフォルトをRealtimeに変更し、出力中も入力を継続するよう修正。
   ユーザーが連続会話の改善を確認した。
6. 会話単独では調べ物に答えられないため、ホスト型Responses delegationを追加した。

## 現在の推論設定

- 音声: `gpt-live-1` / `marin` / mono PCM16 16 kHz。
- 推論: `gpt-5.6-terra`、`reasoning.effort=low`、`text.verbosity=low`。
- `max_output_tokens=1536`（推論分を含む1回の上限）、`service_tier=default`。
- ツールはホスト型`web_search`のみ、`tool_choice=auto`、並列ツール呼び出しなし。
- 雑談は委任しない。比較・相談・分析・最新情報は必要に応じて委任する指示。
- 検索は最新情報や検索依頼のときに限定する指示。これは指示による制御であり、
  呼び出し回数や月額料金を強制的に制限する仕組みではない。
- `store=false`。追加の中継サーバーやMacでの推論処理は不要。

## 実機で確認した結果

最新の約8分間の会話ログで、バックエンド生成6回がすべて`completed`となった。
Web検索完了イベントは3回。生成開始から完了まで約1.3〜3.6秒。
これはバックエンド処理時間であり、質問終了から音声が聞こえるまでの遅延ではない。
天気に関する回答文と音声出力を確認したが、回答内容の外部照合までは実施していない。
会話中の認証失敗・切断・再起動は検出されなかった。起動時のWi-Fi再接続は発生した。

`delegation created`ログの`target=unknown`は、読んでいる位置にtarget文字列がなかったことを示す。
モデル名は設定値のログであって、サーバーから返されたモデル識別子ではない。
サーバーのセッション開始成功と、ネストしたResponses生成・検索完了イベントを合わせて検証した。

## 残課題: 送受信共通ワーカーの詰まり

- 後半に`GPT-Live work queue full; dropping event`が26回発生。
  これは受信イベント件数であり、音声欠落時間や推論失敗件数ではない。
- 送信音声の破棄警告も発生。警告は間引かれているため、警告行数を破棄総数としない。
- ワーカーは16要素の共通キューから送信音声と受信イベントを順番に処理する。
  Opus/PCM変換と同期WebSocket送信も同じワーカーで実行するため、
  CPU負荷・通信待ち・バースト受信のいずれも滞留につながり得る。
- Wi-Fiのbeacon timeout / probeログも繰り返された。因果関係は未確定。
- Terraの推論はクラウドで実行される。実機CPUがTerraを実行しているわけではない。

次はキュー滞在時間、変換時間、送信所要時間、イベント種別ごとの破棄数を計測する。
その結果に基づき、送受信ワーカーの分離、不要な高頻度イベントの削減、音声経路の
変換負荷削減を検討する。キューを大きくするだけでは遅延やメモリ消費を増やし得る。
自己音声の回り込み、入力のピーク飽和、長時間の会話品質も別途評価する。

## 検証・バックアップ

- ESP-IDF v5.5.4でビルド成功、アプリ領域サイズ内、esptoolの画像チェックサム正常。
- 実際のC++セッション生成関数をホスト上で実行し、生成JSONのモデル、推論量、
  上限、検索ツール、音声形式、保存設定を検証した。
- NoAudioProcessorのチャンネル抽出、フレーム化、Stop/再開、コールバックからのStopをテストした。
- 更新スクリプトは正常系、USB違い、画像不整合、パーティション違い、アプリ違い、
  照合失敗、NVS変化、読み取り失敗の8ケースをモックで検証した。
- 実機では更新前イメージ照合、アプリだけの書き込み、書き込み後照合、NVS保持を確認した。
- 16 MB全体バックアップはローカルで保持。最初の高速一括読み取りは失敗したが、
  esptool 4.12 / 115200 baud / 分割読み取りで取得できた。
- 今回はOTA0（0x20000）のアプリだけを更新。設定・assetsパーティションは保持した。
  このオフセットは検証した端末の構成であり、他端末で確認せずに流用しない。

実機で使用したリビジョン6のアプリ識別子は[マニフェスト](live-terra-tested-image.json)に記録する。
アプリ本体と更新・復旧用の端末固有ファイルはローカル保存。既存の`firmware/dist`の
配布イメージはこのリビジョンではなく、今回リリースバイナリとして差し替えていない。
生ログは会話文を含み、Flash/NVSダンプは認証情報を含み得るためコミットしない。
